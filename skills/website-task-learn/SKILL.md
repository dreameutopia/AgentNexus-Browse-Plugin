# 网站任务学习

## 目标

把用户描述的「在某个网站上完成某类任务」转化成一套**可复用、可验证、可交付**的操作经验，并最终通过 `skill-create` 沉淀成技能。你不是替用户把这一批任务做完，而是学会「这类任务该怎么做」。

本技能面向**任意智能体与任意可用工具组合**：工具齐全时由你亲自操作；工具受限时（例如只读的视觉助手、插件能力天花板、Python 未就绪）改由用户操作、你负责观察、校验、记录与纠错。**不得因为工具不足而拒绝开始学习**，也不得假装拥有不存在的工具。

## 输入

用户消息中会包含：

- `<goal>`：学习目标；
- `<user-notes>`：用户对学习过程的要求或注意事项（可能为空）；
- `<target-page>`：用户打开学习页时所在的目标页面（url / title，可能缺省）。

`<user-notes>` 是用户对过程的明确要求。只要不与事实、平台规则、安全边界冲突，优先遵守；冲突时先说明原因再继续。

若系统提示中出现 `<capability-boundary>`，表示本轮部分工具被裁剪。以该边界为准选择学习方式，不要尝试调用被裁剪的工具。

## 阶段 0：能力自检、澄清与任务抽象（必须先完成，未获确认不得开始实践）

### 0.1 能力自检与学习模式判定

在开始任何操作前，先确认本轮**真实可用**的工具，并选定一种学习模式写进学习契约：

1. **自主操作模式**：具备浏览器交互/导航能力（如 `browser_interact`、`browser_navigation`、`browser_tabs`、`js_run`）。你亲自执行全部步骤，并自行验证结果。
2. **用户协作模式**：只具备观察/读取能力（如 `screenshot`、`vision_gui(read)`、`browser_observe`、`browser_get_page_info`、`read_website`、`browser_wait`），没有代操作能力。你通过 `interact` 给出逐步指令，由用户点击/输入；每次操作后你重新观察并核对结果，负责纠错与记录。
3. **观察记录模式**：交互与观察能力都受限。用 `read_website` / `interact` / `plan_tool` / `note_tool` 尽可能获取信息，明确标注哪些步骤**未由你直接验证**，并把限制写进最终交付。

模式判定以工具清单为准，不凭智能体名称猜测。模式变化时（例如用户中途开启/关闭能力）重新判定并告知用户。

### 0.2 读现场

用当前可用的观察能力读取目标页面（`read_website`、`browser_observe`、`browser_get_page_info`、`screenshot` 等），确认站点、页面类型、登录/权限状态与可操作入口。不要凭 URL 或标题猜页面结构。完全没有读取能力时，用 `interact` 请用户描述或确认现场状态。

### 0.3 找歧义

逐项判断是否存在会影响学习结论的决策点，包括但不限于：

- 站点与页面范围（只学当前页、某个流程，还是整个站点）；
- 账号、登录、权限、地区、语言、套餐等前置条件；
- 任务的输入与输出（用户提供什么、最终要得到什么、成功判据是什么）；
- 批量规模、筛选条件、排序、分页、重复项与异常数据的处理；
- 是否存在提交、发布、支付、删除、发消息等不可逆或高代价操作；
- 时间、频率、验证码、风控、隐私与数据留存限制；
- 明确不学什么（非目标）。

### 0.4 问清楚

有实质歧义时，用 `interact` 向用户提问。一次最多问 3 个最关键的问题，优先给选项，避免开放式盘问；能从页面或用户描述确认的不要重复问。没有实质歧义就不要为了流程而提问。

### 0.5 抽象任务与确认契约

把目标整理成可复用的场景定义：

- 场景名称与一句话目标；
- 适用范围与前置条件；
- 输入、输出与成功判据；
- 主流程与关键分支；
- **本次采用的学习模式**，以及该模式下哪些步骤由你验证、哪些由用户操作后你复核；
- 已知风险、不可逆操作与安全边界；
- 非目标与不覆盖的情况。

用 `interact` 把上述「学习契约」呈现给用户，明确询问是否接受、是否需要修改。只有用户明确接受后才进入阶段 1。用户要求修改时，回到 0.3 重新收敛，不要带着未确认的假设开工。

## 阶段 1：设计学习案例（至少两个，覆盖差异）

1. **按通用性设计案例**：从学习契约中提取会影响操作路径的变量（例如筛选条件、状态、数量、分页、空结果、异常项、不同账号权限），设计 **2–3 个代表性案例**。至少包含：
   - 一个主流程 happy path；
   - 一个关键差异分支（不同筛选/条件/状态）；
   - 一个边界或异常场景（空结果、缺字段、重复项、权限不足、失败反馈）。
2. **按学习模式落案例**：
   - 自主操作模式：每个案例写成你可独立执行的步骤与预期反馈；
   - 用户协作模式：每个案例写成给用户的逐步指令（入口、操作、预期反馈），并约定每一步之后你如何观察复核；
   - 观察记录模式：写清可读取的证据来源与无法验证的部分。
3. **给用户一个参考示例**（按实际站点替换，不要照抄）：
   - 若目标是「在招聘网站按不同要求投递岗位」，案例可以是：A) 按城市 + 薪资筛选后投递 2 个岗位；B) 按经验 + 远程筛选后投递 1 个岗位；C) 筛选结果为空或岗位已下架时的处理。每个案例都要写清输入、预期结果和验证方式。
4. **安全边界**：优先选择可撤销、低代价、可重复的样本。遇到提交/支付/发布/删除/发消息等操作，先向用户确认是否允许用最小样本真实执行；不允许时用「执行到提交前一步 + 明确标注未真实提交」的方式学习，并在结论中写清限制。绝不为了跑通而绕过验证码、风控、权限或平台规则。
5. **落计划与记录**：用 `plan_tool` 为每个案例建立可独立验证的步骤；用 `note_tool` 建立学习笔记，记录契约、模式、案例矩阵、样本与预期结果。

## 阶段 2：执行与验证（至少两轮完整实践）

1. **逐案例端到端执行**：从干净状态开始，按真实用户路径推进，不只验证单个选择器。
   - 自主操作模式：由你执行；
   - 用户协作模式：由用户按指令操作，你每步重新观察；
   - 观察记录模式：只做可验证的读取，其余明确标注。
   记录：
   - 入口 URL、页面状态与必要等待；
   - 稳定的定位方式（文本、角色、标签、稳定属性；避免临时 class、随机 id）；
   - 每一步的输入、反馈、加载/校验/弹窗/跳转；
   - 失败后的恢复动作与重试边界。
2. **实时留痕**：每完成一个关键步骤立即 `note_tool(action="append")`，不要等最后回忆；计划状态用 `plan_tool` 同步。笔记要区分「已验证事实」「用户反馈」「推测」。
3. **两轮原则**：至少完整跑通 **两个不同案例**，其中至少一个与第一个案例在关键条件上不同。只有一轮成功不能证明可复用；如果第二个案例失败，修正规则后重新跑，直到两个案例都通过，或明确记录无法覆盖的原因。
4. **验证结果**：每轮结束都用当前可用的只读方式复核结果（列表/详情/状态/提示/计数/截图），不要只看「操作成功」。用户协作模式下由用户执行后你复核；你无法直接验证的步骤必须标注为「用户确认，未经独立验证」。
5. **提炼规则**：两轮结束后，把差异归纳成可复用规则：前置条件、稳定定位、分支判断、等待与重试、成功判据、失败停止条件、不可逆操作保护、所需能力与替代路径。删除只对单个样本成立的偶然细节。
6. **能力不足时**：不要反复尝试不存在的工具。连续两次因能力缺失无法推进时，向用户说明缺什么、当前能学到哪一步，并把可复用结论降级为「已观察 + 待验证」。

## 阶段 3：沉淀为技能

1. **加载 skill-create**：调用 `skill_tool(action="load", skill_id="4")`，严格按照 skill-create 的规范创建技能。不要跳过加载直接 create。
2. **命名与描述**：
   - name 用「站点 + 精准操作」的 kebab-case，例如 `example-apply-jobs`；不要用泛化的万能名称。
   - description 写清适用场景、精准 URL / 路径范围、输入对象、前置条件（登录/权限/页面类型）、所需能力与不适用范围。只描述适用性，不写实现细节。
3. **正文**：只提交 content（不含 frontmatter），至少包含：
   - 目标与范围、前置条件；
   - 可靠入口与可复用工作流；
   - 关键分支、等待/校验/弹窗处理、失败恢复与停止条件；
   - 结果验证与交付方式；
   - **不同能力下的执行方式**（自主操作 / 用户协作 / 观察记录）；
   - 已验证事实与仍未验证的假设分开写；
   - 安全边界与不可逆操作保护。
4. **allowed_tools**：只声明实际需要且已验证可用的工具；若某工具只在部分智能体可用，在正文里写清替代路径，不要把它写成硬前提。
5. **资源**：需要脚本/模板时先用 `file_util` 在工作区整理并用小样本验证，再随 create 的 files 提交；正文按资源路径引用，不要把脚本全文塞进正文。
6. **创建与核验**：调用 `skill_tool(action="create", ...)`，检查返回的 `skill_id`、资源路径与智能体关联结果。失败时按错误修复，不要重复创建同一份技能。把技能 ID、名称、适用范围写入笔记。

## 阶段 4：交付与验证建议

1. **总结学习结果**：向用户说明：
   - 本次采用的学习模式与原因；
   - 学到的可复用流程与关键分支；
   - 实际跑通的案例与证据（区分 AI 直接验证 / 用户操作后复核 / 未验证）；
   - 仍未验证的假设、站点限制与安全边界；
   - 创建的技能 ID / 名称 / 适用范围 / 所需能力。
2. **询问是否验证**：用 `interact` 询问用户是否要基于刚创建的技能做一次验证。
   - 用户同意：请用户给出或确认一个验证任务（可以与学习案例不同），然后加载新技能并在干净状态下端到端执行一次；按「通过 / 不通过 + 证据 + 问题」报告。不通过时用 `skill_tool(action="edit", ...)` 修订后重新验证，不要把未验证的修订说成已通过。
   - 用户拒绝：明确提示「建议在后续真实使用中先观察两次这个技能是否符合预期」，并列出需要重点观察的判据（入口、定位、等待、分支、结果校验）。
3. **结束**：本阶段没有专用终止工具。完成总结与询问后正常结束本轮对话即可；不要为了「结束」而调用不存在的工具。

## 通用准则

- **先确认后执行**：阶段 0 的契约未获用户明确接受，不得开始真实操作。
- **能力自适应**：以运行时真实可用工具为准选择模式；工具不足不是拒绝学习的理由，假装拥有工具才是。
- **真实验证**：每个结论都要有证据；无法独立验证的步骤必须标注来源与限制。
- **最小样本**：批量任务只做代表性样本，不擅自执行整批；不可逆操作先征得同意。
- **稳定优先**：优先使用语义化、稳定的定位方式；临时 DOM 引用、随机 id、截图坐标只作辅助。
- **失败不掩盖**：同一方案连续失败 3 次就换通道或向用户说明；登录墙、验证码、权限不足不得绕过。
- **上下文变薄时**：立即 `plan_tool(action="read")` + `note_tool(action="get")` 双回读，按笔记与计划恢复，不凭印象继续。
- **保护隐私**：不把密码、Cookie、令牌、个人敏感信息写进笔记或技能。
- **不虚构**：没跑通的案例不要写成成功；没验证的技能不要声称可用；用户执行的步骤不要写成你执行的。
