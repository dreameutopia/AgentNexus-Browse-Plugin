# 网站学习：运行链路与产出契约

## 原有问题

- 编排只按 strategy 选择学习工具，视觉目标和文本目标的视觉辅助共用同一工具组。
- 视觉学习继承 GUI 工具，没有 `browser_observe`、`browser_interact`、`browser_page_exec`，无法沿用文本观察与交互。
- 文本目标使用视觉策略时，提示词强制 `vision_gui(action="mark") → vision_gui(action="inspect")`，将 DOM 取证不必要地绑定到截图标注。
- `browser_observe` 能枚举和过滤，却缺少通过当前节点引用读取指定元素完整属性与 XPath 的入口。
- 技能只要求笼统的“工作流”，没有独立完成计划及逐项对应的具体操作讲解；原因、双线索、隐藏入口等未形成统一规范。
- 提交工具仅检查正文非空与长度，未知工具还会被静默剔除，可能留下无法执行的技能。
- 重新学习清空验收报告，学习者看不到上一版失败在哪里。

## 运行链路

`SiteLearnModal.vue` 收集目标站点、自然语言目标、额外描述（可选）、目标操作模式、学习策略、模型和自动验证选项。
额外描述按码点限制为 6000 字，保留换行，确认页可核对；返回修改保留，新学习意图清空。旧配置缺该字段仍可用。

`learn-validate.ts` 校验配置：视觉目标固定使用视觉策略；凡需要图片的组合，模型声明与协议都必须支持图片。

`use-learn-session.ts` 创建专用会话，学习段按 `getSiteLearnScenario`（目标模式 × 学习策略）、验证段按 `getSiteValidateScenario`（只看目标模式）选择工具，用 `buildLearnPrompt` / `buildValidatePrompt` 装配指令。两段装配都传 `disableSkillDiscovery`：不注入技能发现清单与 `load_skill`（固定分区的技能目录句子同步切换为「本会话不提供技能目录」），既有技能不能污染试错过程、不能破坏盲测，也不能经技能携带工具把 `vision_gui` 注入文本目标。
提交回执先经 `asSkillDraft` / `asValidationReport` 形态守卫，再由 `reconcileSkillDraft` 与目标模式对账：mode / 模式标签不一致就地纠正，文本目标混入的视觉工具与学习内部工具被剥离，剥离后无可用工具则按无产出处理——模型的偏差不会落成错误模式的技能。
学习者使用计划推进、笔记留证，**以调用 `submit_skill` 作为唯一结束方式**（见下节「终态分化」）。

**交付物是可复用的完整流程手册，而非完成整个批次**。学习和验证共用 `SAMPLE_GUIDANCE`：
批量任务默认用 2–3 条有代表性的差异样本核对端到端路径、结果回读和迁移性；单次任务不凑数量。
批量循环的遍历、业务标识去重、逐条记账、失败隔离、断点恢复及终止条件仍须写清；抽样数量不是最终技能的执行上限。
默认路径与有识别条件的特殊处理分开，未证实范围如实注明，关键路径未证实不能判通过。
已完成的发送/投递只读核对，不为验证而重放，也不通过额外写操作制造异常。

额外描述作为用户过程规范进入两个阶段，优先按其推进；现场证实的步骤和用户澄清必须进入正文。
与现实不符、缺少条件或无法继续时调用核心工具 `interact` 等真实答复，拒绝或未答复不继续依赖该答复的操作。
两阶段使用共享 `InteractDialog` 与回调；用户等待不消耗主动运行时长，退出/终止清理待答问题。

验证先独立检查原文，发现问题允许有界诊断和通用修订；不能凭经验补做后声称原文通过。
`submit_validation` 可在 `passed=true` 时提交 `revision={body,summary,evidence}`：完整替换正文、修改原因、1–6 条实际复核证据。
修订须保留原任务、身份、模式及工具权限，默认路径和特例分开说明；受影响路径重新核验后才提交。
工具与回执守卫都检查结构、长度、证据和通过状态；坏修订不会被静默丢弃后误认原文通过。
编排只接受对应终止工具的回执，合法修订仅替换草稿正文，并同步会话回放和最终管理中心交付；未通过时保留原草稿。

## 上下文阈值与压缩（两段如同两个独立普通会话）

学习与验证和普通会话共用同一套上下文保护：每轮请求按「系统提示词 + 工具定义 + 消息」
全量计量，达到 95% 触发运行中压缩，压缩产物替换为一条摘要系统消息继续运行——
长探索不会因窗口耗尽而整段中断，摘要的任务分区（`<task>`/`<progress>`）保住已探明的线索。

压缩边界由 `compaction-boundary` 纯模块规划：优先取「最后一条用户消息之前」
（多轮对话与视觉续拍的常态）；学习/验证这类**单用户消息的长自治运行**没有该边界，
按原子组（assistant 工具调用与其结果互为整体）回退——保留最近若干完整轮次
（约 30% 窗口预算），其余进入摘要，协议配对约束不破坏。压缩失败进入冷却重试
（间隔 3 轮），不整段熔断。

两段上下文**互不接续、互不加总**：验证以空历史冷启动（盲测隔离），收尾轮只带本阶段记录；
压缩状态经本条助手记录的协议检查点（`modelContext`）持久化——学习会话的转录连续、
模型上下文分叉，单一会话级压缩点无法表达分叉历史，也不允许把学习段摘要混入验证段。
学习结束（`done`）后会话恢复普通对话，其历史自然衔接两段转录。
状态条与用量环经引擎 `context-usage` 事件显示**本阶段**最近一次请求的真实占用。

## 终态分化：成功 / 失败 / 被阻断

`submit_skill` 的 `status` 决定本次学习的终态，三条路都是**一等终态**：

| status | 含义 | 必填字段 | 产出 |
| --- | --- | --- | --- |
| `success` | 样本端到端路径和关键差异已证实，掌握完整推进方法 | `name` / `description` / `category` / `body` / `allowedTools` / `mode` | 技能草稿 → 交付管理中心 |
| `failed` | 流程没走通，但原因已定位 | `reason` / `detail`（`findings` / `suggestion` 强烈建议） | 失败报告 → 失败弹窗 |
| `blocked` | 被必须由人完成的前置条件挡住（登录、验证码、扫码、付费、授权） | 同上 | 失败报告 → 失败弹窗 |

**为什么失败必须是终态而不是「模型自己说一声」**：

- 引擎只认 terminal 工具的**成功执行**；模型输出一段文本总结时，运行照常结束，
  编排层拿不到任何确定信息，用户只看到「没产出」。
- 提交校验要求正文合格（七个小节、编号逐项对齐）。模型受阻时往往正写不出
  合格正文，提交失败拿回的是参数错误——它既不知道可以体面收尾，也拿不到
  「卡在哪」的答案，于是反复重试直至放弃。
- 失败是**有产出**的：`findings` 承载已走通的步骤、已确认的定位线索与踩过的坑，
  用户拿到的不是一句「失败了」，而是「学到了什么 + 卡在哪 + 下一步怎么办」。
  失败报告随工具回执留在会话记录里，结束后仍可回看。

`reason` 取机器码（`LEARN_FAILURE_REASONS`）：`login-required` / `captcha` /
`permission-denied` / `target-missing` / `flow-broken` / `locator-unstable` /
`page-unreachable` / `timeout` / `other`。前三项表示「必须由人完成」
（`isHumanBlockedReason`），UI 据此给出「等待人工介入」而非「换个策略重试」的建议。

**status 与 reason 不一致时只提示、不拒绝**：终态提交失败就等于「本次学习没有结论」，
代价远大于分类偏差。工具层在回执里指出偏差（`consistencyNote`），照收不误。

**字段要求是分层的**：形态问题（缺 `status`、未知 `reason`、空 `detail`）返回可读错误让模型自纠；
`findings` 则是宽容的（形态不对按空处理）——它是「建议填」，不该成为一次终态提交失败的理由。

## 强制收尾（终态必须被调用）

高级设置折叠展示两阶段独立预算，默认均为 60 轮 / 30 分钟，关闭验证时不提交或校验隐藏的验证预算。
轮次、分钟数必须是大于等于 1 的安全整数，分钟转毫秒亦须保持安全整数。
轮次、时长或连续工具失败触限时，模型暂停，`LearnDialog` 提供三项：

- 继续：默认追加 15 轮，可改为任意有效正整数；当前运行保留完整上下文，重新开启当前时长上限的时间窗口。用完再次询问，可反复追加。
- 总结：明确切到现有 `forceSubmitMessage` / `forceValidateMessage` 收尾指令；收尾本身触限仍由用户选择。
- 丢弃：二次确认后结束引擎，再清理会话和草稿；取消确认回到预算选择，不恢复执行也不自动总结。

`resetBudgetOnContinue` 只由本地学习/验证流程开启，不改变普通对话的延续语义；新增 N 轮恰好提供 N 次模型请求。
弹窗的等待时间不侵占新窗口；App 直接转发选择事件的全部参数，避免丢失用户输入的轮数。

引擎对「模型只回了一段文本」没有任何约束，这条历史上经常被违反。编排层
用两段式把它变成硬约束：

1. 正常跑完并交了终态 → 按终态分流（草稿 / 失败报告 / 验收结论）。
2. **自然结束却没交终态 → 自动补一轮收尾轮**（`forceSubmitMessage` / `forceValidateMessage`：
   「成功就 success，失败就 failed，不必凑正文」），不打断用户、不弹窗。
   收尾轮**携带本次探索的会话记录**——冷启动的收尾轮会从头再摸索一遍，
   很可能再次空手而归；带上自己的探索痕迹，模型才能把已知线索直接写成
   草稿或失败报告。验证收尾只带本次验证记录，不混入学习历史或先前遗留摘要；基线读取失败时不携带未知来源历史。
   收尾轮另有更紧的预算（8 轮 / 5 分钟，见 `LEARN_FORCE_SUBMIT_LIMITS`），
   只用于收尾，不允许再展开探索。
   历史按记录边界截断（最近 16 条，见 `LEARN_FORCE_SUBMIT_HISTORY`）：
   每条记录的协议历史自包含（助手消息与其工具结果同属一条），不会截出悬空 tool_call。
3. 补跑后仍未交 → 以**确定的**失败原因收场（`buildMissingOutcomeFailure`），
   不再靠「可能是没调用 submit_skill」这种猜测。

**用户决定优先于兜底**：触限不自动转总结，只有明确选择“总结”才切换；确认丢弃后直接清理，不补跑收尾。

失败弹窗（`LearnDialog` 的 `learnFailed` 态）的按钮按阶段分叉（见 `allowedChoices`）：
学习阶段是「带着这些信息重新学习 / 结束」（此时没有草稿，结束即放弃）；
验证阶段是「重新验证这个技能 / 仍要创建」（草稿已学成，不能白丢）。
「重新学习」把失败报告作为反馈注入下一轮 prompt 的 `<previous-failure>` 分区；
盲测未通过的问题清单走独立的 `<previous-validation>` 分区——两者刻意分开，
模型不会拿「技能写错了」的心智模型去改一份根本不存在的技能。

## 成果保全（草稿永不白丢）

学习是长任务，草稿是几十轮探索的唯一沉淀。以下规则贯穿全链路：
**持有草稿时，任何路径都不得把它丢掉**。

| 场景 | 处置 |
| --- | --- |
| 验证不通过，弹窗被顶替 | 收敛值取 `create`（交付草稿），不取「不推进」 |
| 验证段硬失败（引擎错误） | 先交付草稿并提示错误（`handleFatalFailure`），再谈失败 |
| 验证段没交结论，用户收场 | 弹窗提供「仍要创建」，不提供「放弃」 |
| 终止流程进行中 | 一律不交付（终止的语义是整体丢弃，由终止流程统一清场） |
| 草稿形态非法 | 写入前自检（`isDraftPayload`），当场判失败而不是写进去让 hub 侧退回空表单 |

## 终止流程

终止是最高优先级的用户意图，**不让位于任何在场的弹窗**（否则模型撞轮数上限
弹出收尾弹窗时，用户既不能继续也不能终止，只能干等）：

1. 点终止 → 结算在场的运行中弹窗（收尾守卫）→ 引擎停下；
2. 弹终止确认 → 确认则整体清理（abort → 等运行退出 → 删会话 → 清草稿 → reset）；
3. 取消则给一个确定结论收场（运行已停，不能让状态机悬空）。

装配与运行包在同一个 promise 里（`runEngineOnce`）：`activeRun` 在装配开始时就占位，
否则用户在装配阶段点终止，终止逻辑看不到在跑的运行，会删掉会话之后又让运行启动，
在已删除的会话上写出孤儿记录。装配完成后再检查终止标志，此时绝不启动运行。

## 跨页交付

草稿以独立 ID 存入 `chrome.storage.local` 持久交接队列，不读取即删、不过期。
同一会话的同一成果重试使用相同 ID；旧版单槽草稿先复制迁移并保留原数据。
深链 `#new-skill?id=<ID>&t=<nonce>` 只提示待接收成果，不重置已有编辑器。
管理中心保留各分区状态，提示先保存当前编辑；用户明确确认后才进入预填的新建技能。
智能体/技能编辑尚未结束时禁止接收，跨标签接收使用 Web Locks 互斥。

预填期间保存包含资源文件、模式与未完成资源编辑的恢复副本；刷新后可主动恢复。
原始成果始终保留。只有技能落盘确认成功才标记交接完成；写入或确认失败保留表单，
用技能 frontmatter 的交接 ID 确保重试不重复创建。保存期间阻止交互并检测异步内容变化。
导航失败可手动打开管理中心；交接写入失败不导航，侧边栏提供下载和重试。
双存储故障时内存副本只在当前页面存活，必须提示用户保留页面并下载，不能宣称已经持久保存。

侧边栏恢复提示通过 `use-learn-recovery` 读取同一份保存回执，不以转录里仍有草稿判断是否待创建。
storage 事件即时同步，页面重新获得焦点/可见及点击创建前再次核对；已保存时隐藏整组创建/下载/忽略入口，不再导航。
“忽略本次学习”经独立自定义确认弹窗后，持久写入 `recoveryDismissed`：侧边栏和管理中心待接收队列同时隐藏。
不删除会话、原始成果或已建技能，也不使管理中心已经打开的编辑器失效；编辑保存与忽略共享交接写锁，状态可安全合并。
忽略写入失败保留提示并在弹窗中显示错误；切换会话、组件卸载及旧异步回读不会把状态套到另一个会话。

## 自主解决

`LEARN_SELF_RESCUE` 分区给出明确的升级阶梯：遇到报错、找不到元素、页面没变化、
结果为空时**先自救，再考虑失败**——读懂错误语义 → 换定位通道 → 换操作通道 →
换信息通道 → 换路径，每级换一种手段；同一方案最多 3 次且每次必须换方案。
只有必须由人完成的前置条件或目标确实不存在时，才允许提交 `failed` / `blocked`，
且必须在 `findings` 里写清「已经试过什么」，让下一轮不用重走死路。

启用自动验证时，以空历史开始第二段运行，只给最终技能和验收目标，通过 `submit_validation` 返回报告。
验证只提供技能声明且符合目标模式的执行依赖，以及核心交互/计划、笔记、终态、视觉自动截图基础能力。
模型可见的工具 schema 与可执行工具使用同一边界，默认会话工具也会被过滤，不能靠更宽环境掩盖依赖缺漏。
验证从技能的起始条件重新执行，检查步骤、原因、定位证据、文本兜底、视觉描述及完整范围。
`issues` 仅表示未解决的执行/复用问题；有问题不能传 `passed=true`。可选建议独立放 `suggestions`。
通过需要实际 `evidence`（样本/差异状态、业务回执与覆盖限制）；有修订时可沿用 `revision.evidence`，不重复填写。
修订必须在原声明能力内完成并复验；必要工具缺失又无法用已声明能力修正时应不通过，交回学习完善依赖。
用户选择重新学习时，报告的问题清单会注入下一次学习；验证本身始终不带学习过程。

草稿交给 `learn-draft-store.ts` 的持久交接队列，再打开管理中心提示用户主动接收，不自动覆盖现有编辑。
新结构只约束学习工具的新提交，不迁移或拒绝已有手写/导入技能。

学习策略先跑通最小端到端闭环，再补关键差异，不先滚完整个列表。2–3 个样本不等于2–3次新发送，
可通过已有完成状态的只读回验检查差异。样本数量、写操作预算与未来批量执行数量分别处理。
每次动作核对对应业务后置条件；页面 load、临时 disabled、列表顶部或一次固定总量都不是通用成功/去重/终止保证。
已决定的范围和路径只有新证据出现才重新讨论，计划按阶段更新，证据反证旧判断时更正笔记。

这些原则参考 [Playwright 的语义定位、隔离与条件断言](https://playwright.dev/docs/best-practices)
和 [AWS 的明确幂等契约与安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)，
不依赖任何特定站点的 DOM、URL 参数或列表数量。

## 学习工具与专属引导

工具清单与 prompt 都是学习域**自有**配置：`tool-presets` 的学习/验证场景不展开 `AUTOMATION_TOOLS` / `VISION_AGENT_TOOLS`，`learn-prompts` 不 import 两个动作智能体的 SOP（`ELEMENT_INTERACTION_SOP` / `VISION_ACTION_SOP`）。文本通用助手与视觉通用助手的配置、提示词演进不会影响网站学习，反之亦然。

| 目标模式 | 学习策略 | 场景 | 工具与引导 |
| --- | --- | --- | --- |
| 文本 | 文本 | `siteLearnText` | 完整文本观察/交互与页面脚本，不启动截图循环；验证仅靠文本线索能重定位 |
| 文本 | 视觉 | `siteLearnVisionForText` | 文本全套 + `screenshot`（自动截图**仅用于帮助理解屏幕元素**）；**不提供 vision_gui**，操作与取证一律走 DOM 文本通道，截图不得成为执行前提 |
| 视觉 | 视觉 | `siteLearnVision` | 文本全套 + `vision_gui` 手势 + `screenshot` + `browser_window`；按需 mark→inspect 核对，额外记录位置、外观、组件形式、周围锚点和交互反馈 |

共同文本工具（`SITE_LEARN_DOM_TOOLS`，学习域自有清单）：

- `browser_observe`：`controls/buttons/inputs` 枚举；`element` 查询指定节点属性；`structure/accessibility` 处理复杂页面。
- `browser_interact`：点击、填充、聚焦、键盘、输入和容器滚动。
- `browser_page_exec`：常规观察不足时探测页面结构或组件作用域。
- `browser_get_page_text`（核心注入）、`browser_get_page_info`、`browser_navigate`、`wait_page_load`、`browser_go_back_or_forward`。
- `browser_get_all_tabs`、`browser_switch_tab`、`browser_network_capture`、`web_search`、`generic_wait`。
- `plan_tool`、`note_tool` 与交互征询工具（同为 CORE_SESSION_TOOL_IDS 核心注入，所有会话恒定可用，学习域逐步留痕/记录卡点的用法由 learn-prompts 约束）、学习终止工具 `submit_skill`。

视觉目标组合额外具备：`vision_gui`（10 个 action，参数由 schema 与学习域自有的 `<vision-gui-tool>` 分区描述）、`screenshot`、`browser_window`；文本目标×视觉策略仅额外具备 `screenshot`。

`<vision-gui-tool>` 分区是 runtime-builder 的协议标记：学习提示词携带该分区时，引擎不再追加视觉通用助手的 `VISION_ACTION_SOP`。视觉目标在该分区放学习域自有的手势契约（含按需 mark/inspect）；文本目标放「本阶段没有视觉 GUI 工具」的禁用分区，同时显式禁止模型激活技能清单中的视觉工具。

视觉目标允许按需使用 `vision_gui` 的 mark/inspect action：先看原图和 DOM，仅在无文字图标、同名控件或视觉区域难以对应节点时打标；下一张截图出现数字框后再 inspect，数字不用于点击。

验证工具将 `submit_skill` 换成 `submit_validation`，视觉能力只按目标模式分叉（`getSiteValidateScenario`）。验证 prompt 同样只用学习域自有的工具契约块，不引用动作智能体 SOP。

## 元素取证与执行

先 `browser_observe(view="buttons"/"inputs"/"controls")` 枚举，自动覆盖可访问 frame，不传 `elementId/frameId`；读取节点详情时才传该行 `elementId` 和 `frameId` 到 `view="element"`，不混入过滤或分页参数。调用契约由工具 schema 维护，学习/验证提示词只补充探索、消歧与取证策略。
指定属性查询返回 XPath、文字、属性、关联 label、值与状态、选项、frame URL、frame 内矩形和外观，不返回密码值。
读取复用文本工具的节点注册、有效期与 frame 路由；过期/替换/导航后必须重采。Shadow 内返回作用域及局部路径，不冒充可直接查询的文档 XPath。

执行优先用 XPath，核对 `Hit`、文字与上下文。未命中时必须去掉 XPath，再单独按文本/属性 regex 搜索；两者同时传入为 AND，不是 OR。
过滤结果会包含未命中候选，不能把第一行或任意返回行当作匹配。XPath 是重新定位线索，不是可直接传入交互工具的节点引用。

技能保存至少两条独立可重采线索，优先 XPath 与文本。无文本如实说明，改用 placeholder、aria-label、name、role、区域等。
视觉目标在此基础上加位置/外观；Canvas 等无 DOM 时注明限制和视觉替代。文本目标无法覆盖必要步骤时不能假称可执行。
固定 elementId、frameId、snapshotId、screenshotId、数字标签或坐标不应成为长期定位依据。

## 最终产出

`status=success` 时产出技能草稿：`name` 为“平台-任务简短概述”，兼容当前技能库的小写英文 kebab-case，例如 `pinduoduo-search-products`。
`body` 为无 frontmatter 的 Markdown：

1. `## 目标`
2. `## 前置条件`
3. `## 完成计划`：按 `1.`、`2.` 拆成未来执行者可逐步推进的细致单元。
4. `## 具体操作讲解`：按 `### 1.`、`### 2.` 与计划逐项对应，每步说明动作、原因、目标线索、操作方式、成功判据与注意/恢复。
5. `## 分支与坑点`
6. `## 完成判定`
7. `## 边界`

输入关键词、条件等参数化，元素文案与 XPath 保留真实证据。“全部”目标必须说明分页/无限滚动、去重、终止和实际覆盖范围。
隐藏内容写触发顺序，滚动写方向及容器，避免用“继续操作”等泛化描述代替实际步骤。

`status=failed` / `blocked` 时产出失败报告：`reason`（机器码分类）、`detail`（卡在哪一步、期望什么、实际什么）、
`findings`（已探明的可复用知识）、`suggestion`（建议的下一步）。失败报告**不含技能正文**——
它不是残缺的技能，而是这次学习的确切结论。

`learn-output-contract.ts` 与提示词、提交工具共用小节定义。提交校验标题、非空、顺序、计划/讲解连续编号及数量一致；拒绝未知工具、阶段提交工具和文本技能依赖的视觉工具，移除冲突模式标签。
静态校验不能证明 XPath 真实、描述正确或网站流程可用，语义与业务结果仍由实际探索及可选盲测检验。

评估设计参考 [Anthropic 的 Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)：区分执行轨迹与实际结果，用差异样本和结果回读检查行为。2–3 条是本产品的默认探索范围，不是统计上的普遍可靠性保证。

## 回归检查

- `npm run test:tools`：工具注册、工具矩阵、三种提示词、提交失败自纠、结构校验和真实序列化 DOM 属性读取等；`site-learning` 用例额外断言：
  - 学习/验证的隔离契约（文本目标无 `vision_gui`、prompt 不内嵌动作智能体 SOP、`<vision-gui-tool>` 协议分区按目标模式分叉）；
  - 终态分化契约（`status` 三值、失败提交不必交正文、失败报告的 reason/detail/findings 守卫、status 与 reason 不一致只提示不拒绝）；
  - 失败反馈与盲测反馈的分区分离（`<previous-failure>` / `<previous-validation>`）；
  - 强制收尾轮消息（成功/失败两条路 + 免除失败时的正文义务）；
  - 防御性边界（码点计数、形态守卫的长度/数量上限、对账的标签截断、「必须由人完成」的原因分类）；
  - 跨页交付（持久队列、主动确认、编辑恢复、跨标签互斥及幂等保存）；
  - 验收结论的 issues 可选性（通过时不必带空数组，不通过时必须带清单）。
- `npm run test:skills`：技能存储/指令装配等兼容性。
- `npm run test:vision`：截图、坐标、标注和 GUI 交互契约。
- `npm run compile`、`npm run build`：类型检查与扩展构建。

测试使用 DOM fixture 和模拟扩展 API；不等价于真实站点登录态下的端到端学习效果评测。
