# Vision Action 能力评估（2026-11-03）

当前定位：具有安全释放、截图绑定和诊断能力的 Chromium 网页视觉操作驱动。
它不是全桌面机器人，也没有完成“任意模型 × 任意网站”的成功率基准。不能声称能够完成一切人类任务或已优于其他智能体。

## 实际能力与边界

| 场景 | 当前能力 | 验证与限制 |
| --- | --- | --- |
| 小目标、DPR、滚动条 | 0–1000 小数点坐标映射完整 CSS 视口，校验 PNG | 多 DPR、实际1×1 CSS像素目标、分数像素、有无滚动条已实测；测试用已知目标坐标验证驱动，不宣称模型能从图中可靠识别1px目标 |
| 点击、多选、长按 | 左/右/中键，1–3击，Shift/Control/Meta/Alt，最长3秒持有 | 修饰键点击已实测；浏览器原生右键菜单不在网页截图控制范围 |
| 像素绘图、拖选、滑块 | from/to + 最多128个必须经过的waypoint，可用右/中键与修饰键 | 路径节点、终点、按钮掩码与释放有测试；不跨截图保持按住，不支持视口外坐标 |
| HTML5拖放 | 原生鼠标序列、终点双移动 | 标准 draggable + dragover/drop + DataTransfer 场景已实测；不等于文件拖放、跨应用拖放或所有框架均已认证 |
| 组件滚动 | 先悬停，百分比或CSS像素delta，支持斜向、修饰键 | 嵌套容器有真实回归；页面阻止滚轮、吸附、到边界时最终位移不能保证 |
| 普通输入 | Unicode字素插入，焦点锁定，可先点击与清空 | 中文、emoji已实测；不生成原生IME的候选选择和composition事件 |
| 自定义编辑器键盘处理 | keys模式对可打印ASCII发送keyDown/input/keyUp；功能键与标点 | 大小写、移位符号、键盘事件已实测；字符物理键映射为US布局，不覆盖所有键盘布局 |
| 快捷键与数字小键盘 | vision_keyboard单个组合，左右修饰键、F1–F24、导航编辑键、常用别名、Numpad数字/运算/Enter | Ctrl+Shift字符值、右Shift位置、Numpad位置、普通/小键盘Enter、F24已做真实Chromium回归；不保证网页CDP触发系统/浏览器保留操作，剪贴板受权限约束 |
| iframe/Canvas/Shadow DOM | 顶层截图坐标输入不依赖DOM标记；DOM检查保留frame/shadow作用域 | 同进程iframe和跨frame标记已实测；Canvas可点但无法读取绘制对象为DOM元素，封闭Shadow无通用DOM检查保证 |
| 多标签和窗口 | browser_window查看，现有导航工具管理网页访问 | 不能点击浏览器标签条；新窗口、权限变化会使旧截图失效，需要重新观察 |
| 上传/下载 | 可结合已有files工具组和明确文件参数 | 不把操作系统文件对话框误称为视觉驱动能力；任意OS文件拖放未实现 |
| 桌面、系统权限、原生对话框 | 不支持本驱动直接操作 | 需要独立OS输入/截图通道；不自动确认未知系统弹窗 |
| touch、笔压、多指pinch | 当前鼠标驱动不支持 | 不用鼠标序列冒充触摸、笔压或多指操作；pinch几何未适配时明确拒绝 |
| 登录、验证码、网站拒绝访问 | 交给用户处理并重新观察 | 不承诺绕过，不加入风控规避功能 |
| 业务成功与实时任务 | 工具进度和截图反馈可用于验证 | 单张截图不是连续视频；高速动画、游戏、位置快速变化目标受模型延迟限制 |

## 拟人化的准确含义

已实现的是有界的可变停顿、移动加减速、轻微曲线、起终点持有、字素间隔。
显式路径优先精确经过节点，精细轮事件优先增量守恒。某些动作（定位到起点、键盘快捷键、文本插入）不等同于人的所有手部和输入法过程。
随机时间不是“真人身份”证明，也不能控制网站对设备、账号、网络、频率、行为目的等信号的判断。
这些节奏用于交互可用性，不把绕过验证码、隐藏自动化或规避风控作为产品承诺。

## 与公开实现交叉核对

- [Anthropic Computer Use 限制](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool#limitations)：官方仍列出延迟、坐标与工具选择错误、滚动可靠性等限制。我们以截图ID/几何校验减少“驱动用错坐标”的问题，但不能消除模型感知与规划错误。
- [Playwright 操作指南](https://playwright.dev/docs/input)：区分普通文本填入与需要键盘事件的逐键输入，并说明 dragover 可能需要两次移动。对应补充 keys 模式与拖放终点移动；未宣称仅靠这些措施即可保证所有编辑器和拖放框架可用。
- [Playwright Chromium 拖放实现](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/crDragDrop.ts)：还维护拖放状态与拖放数据。当前驱动使用通过实际夹具验证的原生鼠标序列，没有宣称实现该框架全部拖放机制。
- [Chrome debugger 文档](https://developer.chrome.com/docs/extensions/reference/api/debugger)：扩展使用受权限和企业策略约束的调试通道，不等于可访问整个桌面。我们保留目标限制与错误返回，不伪装为无限制控制通道。

## 可证明的工程特点

可以验证的特点是：完整截图几何绑定、精细坐标与轮增量、修饰键生命周期、取消传递、事务清理、结构化进度与错误诊断，以及真实浏览器回归。
“比其他智能体更强”的结论还需要统一模型、任务集、环境、时限和重试策略的可复现基准，不从功能列表或单个演示推断。

已补充带坐标变换的原图局部放大、显式条件验收、点位目标守卫，以及共享的观察—执行—验收—恢复协议；这些不等于通用视觉识别或业务成功证明。
后续仍有价值的方向包括：专用OS通道、更完整的长期任务检查点，以及更多真实网站/跨进程frame/富文本编辑器任务回归。
这些应作为独立能力开发和测试，不能通过放宽参数校验或让按键跨截图一直按住来代替。

自动夹具与后续真实模型的任务验收口径见 [任务回归方案](../../tests/vision/TASK_BENCHMARK.md)。

本轮观察/验收设计交叉核对了 [Playwright actionability](https://playwright.dev/docs/actionability)、[可重试条件断言](https://playwright.dev/docs/test-assertions) 与 [Claude Computer Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool) 的观察方式。
采用的是检查可操作性、有限等待明确条件、放大细节等原则，不引入对操作本身的盲目重试，也不假定两个项目的内部实现相同。
