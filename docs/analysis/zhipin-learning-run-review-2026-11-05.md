## 结论

这次过程确实存在明显的绕路。主要原因不是单独的“模型不聪明”，而是三个问题相互放大：

1. **学习的停止条件不清晰**，模型把“学会怎样推进”执行成“尽量探到底”。学习和验证各自滚动到 300 条，为无须执行整批的任务付出大量成本。
2. **网页工具的能力和契约存在摩擦**：observe 和 interact 对 FrameId 的要求相反；观察输出的语义类型容易被误作 HTML 标签；纯文本操作缺少直接 hover；导航可能切换到已有标签；错误反馈没有准确区分未派发与效果未知。
3. **验证没有把“靠模型补救后完成”与“原技能可直接复用”分开**。模型发现定位错误、缺参及工具声明缺漏，使用验证环境额外能力补救后，仍给原技能 passed=true、92 分，没有交付修订。

模型本身也有独立问题：反复讨论已做出的选择、证据外推、临时状态误判、写操作去重依据不足。但仅靠换模型或追加更多“必须遵守”的提示，不能完整解决。

本次应评价为：**有真实成功路径证据，但原技能的可复用性尚未得到充分证明；92 分及“主链路零阻断”的结论过强。**

## 逐阶段问题审查

### 1. 任务理解与探索预算

**01｜没有先确定“学到什么就够了”。主因：旧引导与模型策略。**

L5–8 强调“全部详细步骤”“逐步试错”“完整跑通”，但没有把本任务的证据目标约束成搜索、筛选、详情、打招呼回执、循环机制和少量差异样本。模型很容易把探索深度误当作成果质量。

更合理的做法是先列“待验证知识与停止条件”，例如搜索和筛选各证实一次、详情切换证实一次、已有操作只读核验、另一不同样本验证可迁移性；无需先穷尽全部列表。当前 SAMPLE_GUIDANCE 已改善这一点，但还缺少程序可检查的覆盖记录。

**02｜没有把学习样本数、实际执行数量、扫描范围分开。主因：技能内容与阶段引导。**

验证后半段反复围绕“至少 1 个”“默认前若干个”推敲。这三个数字本应分别表示：学习/验证覆盖样本、真实发送预算、未来执行的用户数量。混在完成判据里，模型只能不断猜测。

2–3 个差异样本并不意味着必须发 2–3 条新消息。已有发送记录、不同按钮状态、不同卡片入口等也可提供只读差异证据。新发送数量应独立确定，不能从“抽样数量”推导。

**03｜没有建立岗位匹配与副作用边界。主因：任务规格不足。**

记录里搜索“AI 实习”，随后选择岗位打招呼，但没有展示用户专业方向、岗位偏好等要求。这些并非都必须追问；然而技能至少应区分“关键词命中”和“详情符合目标”。若标题足以确认当前宽泛目标，可以继续；若相关性或发送数量影响选择，应在首次发送前处理，而不是结束后反复讨论数量。

### 2. 搜索、筛选与隐藏入口

**04｜筛选探测明显碎片化。主因：模型策略，工具能力缺口放大。**

L82–115 连续出现多次短脚本调用，随后才获得 jobType=1902。没有脚本入参，无法逐次判定浪费；但它们显然没有被组织成清楚的“假设—观察—结论”。

应把独立的只读检查合并：目标标签名、父子结构、可见状态、已有属性、是否存在下拉选项。改变页面的动作则逐个执行并观察。不是把所有动作塞进一个大脚本。

**05｜纯文本模式缺少直接 hover 能力。主因：工具面。**

模型最终判断下拉为 hover 触发。当前 browser_interact 只有 click/fill/focus/keys/type/scroll，没有 hover；纯文本学习又不提供 vision_gui。这使“用用户界面正常展开下拉”在此模式下缺少直接操作入口。

页面脚本派发鼠标事件不能一概视为真实指针悬停的等价实现，尤其涉及 CSS :hover 或可信事件时。本次缺少脚本内容，不能确认其采取过哪种模拟。当前 prompt 的自救阶梯写了“悬停”，而纯文本 action 集没有这一操作，仍有能力与指令的不一致。

**06｜URL 筛选是可用方案，但证据等级需明确。主因：技能表达。**

jobType=1902 的直接导航并非天然不符合最佳实践。如果真实确认筛选标签、列表和目标类型变化，它可以是高效路径。问题在于不能仅凭 URL 看起来合理就判成功，也不能把当前有效参数承诺为永久接口。

技能应记为“本次已验证的快捷路径”，保留 UI 路径或无法使用时的明确处理；修改 URL 时保留任务相关参数，并正确编码关键词。具体能否从下拉正常选择，记录没有充分证明，不宜补写为已跑通。

### 3. 滚动与列表覆盖

**07｜学习先滚满 300 条，再验证核心打招呼路径，顺序失当。主因：模型策略与旧引导。**

L141 已证明 15→30 的懒加载，随后继续到 300 才进入关键业务动作（L159）。即使需要学习遍历，也应先用少量加载确认机制、尽早闭环，再有针对性补分支。长列表探索消耗预算，却没有直接提高打招呼主路径可信度。

**08｜验证又滚到 300 条，重复了学习阶段的过度探索。主因：技能把探索痕迹固化为执行步骤。**

L567–625 已经知道只需少量样本，却仍完成 300 条加载。说明生成技能很可能把“学会翻页”写成了“先把结果加载完再做事”。验证者机械复现后，又把达到 300 当成质量证据。

未来执行通常应边加载边筛选、逐条处理、达到用户数量或明确结束条件即停止，而不是先把全量 DOM 堆出来。

**09｜“本次停在 300”被外推成“300 封顶”。主因：模型证据推断。**

一次观察到 300，甚至伴随反馈组件，也不能证明所有查询、账号与排序都固定上限 300。可能是本次结果范围、站点展示限制、后续加载失败或其他条件。

更合适的技能表述是“本次查询观察到约 300 条后出现某状态；通用终止以明确结束信号、加载状态、稳定业务 ID 增量及用户数量共同判断”。反馈组件是否就是结束标志，也需要验证，而不是仅凭其出现在底部推定。

**10｜长滚动脚本使超时后的状态难以判断。主因：模型脚本策略，工具反馈部分正确。**

L145 工具明确提醒代码可能仍在运行、先检查现状，这个提醒是正确的。不能把该超时认定为工具完全未执行。

更好的探索单位是一次或少量滚动，并等待可解释状态：新增稳定记录、加载结束、明确无更多。每段都有限时和本地结果。需要区分“任务时间预算”“工具等待超时”和“页面中的脚本是否停止”。仅提高 timeout 不解决停止与恢复问题。

**11｜计数选择器错误说明知识提取没有可靠回验。主因：技能生成及提交检查。**

L608–615 中 li.card-area 得到 0，随后识别为 div.card-area / li.job-card-box。当前看不到原始技能全文，因此无法判断错误最初如何产生；但验证已经提供实际反证。

正确做法是修订条目定位规则并重新核验；不能只因另一个选择器能用，就把错误保留为“轻微瑕疵”。单纯放宽成任意 class 匹配也未必正确，需确认匹配的是业务条目而非布局容器。

### 4. 定位与工具契约

**12｜observe 与 interact 的 FrameId 心智模型相冲突。主因：共享工具契约的人机设计。**

observe 枚举返回 FrameId，interact 的 DOM 操作必须携带它；但 observe 枚举本身不接受 FrameId，只有 element 详情接受。模型把交互路由信息带回枚举，是可以解释的泛化错误。

四次“我又加了 FrameId”的失败说明模型纠错没有稳定保持，也说明旧工具描述/错误恢复指令不足。当前 observe 已将两类调用分支拆开、增加例子和可执行纠错，这是已完成的改善。本记录不足以证明新契约仍有相同失败率。

**13｜语义角色被当作 HTML 标签，导致错误 XPath。主因：模型理解，观察字段语义放大。**

模型先按 button 标签找“立即沟通”，后来发现真实标签是 a。后面验证也注意到 observe 将 a 展示为 button。语义角色 button 与 tagName=button 不是同一概念。

模型不该猜标签；观察表的 Type 若代表角色，也应明确标明。必要时输出 role 与 tagName 的区别，或按需查看节点详情。不要让执行者必须为了知道“button 到底是不是 button 标签”不断写脚本。

**14｜全页唯一不是稳定的定位契约。主因：模型泛化。**

本次 a.op-btn-chat 只有一个，不等于列表 hover 态、不同分辨率或其他页面状态也只有一个。模型一开始意识到同名按钮风险，这是正确的，但后续又依赖“只有一个”。

应先确认当前详情所属岗位，再在详情区域内定位按钮，核对名称、业务对象和可操作状态。数量只是当次检查，不能代替作用域与对象绑定。

**15｜regex 无命中仍返回大量候选，增加阅读与误用风险。主因：观察输出设计。**

L394–422 的结果 totalHits=0，却仍返回 40/92 候选和后续分页，其中含无关导航与用户信息。返回结构有提示，并非虚报命中；模型也不能把剩余候选当匹配对象。

这种“筛选”实际是匹配优先排序，容易违背调用者的筛选直觉。可考虑明确区分严格匹配结果与上下文候选，在零命中时先给简短结论与恢复建议，按需展开其他候选。改变兼容行为需单独设计，不能直接假设应删除所有上下文。

**16｜滚动的无节点分支缺少足够清楚的 FrameId 契约。主因：工具描述和生成技能。**

L587 缺 FrameId 报错。当前说明强调“DOM 引用必须提供 FrameId”，但文档滚动恰好允许没有 elementId，读者可能认为无 DOM 引用就无需 FrameId。

应明确区分“指定容器滚动”和“指定 frame 文档滚动”，后者仍必须从当前观察确定 frameId。长期技能保存的是获取路由的方法，不能硬编码 0。这一点不能通过“所有操作默认主 frame”草率修复。

**17｜参数错误被包装为可能部分生效，扩大恢复成本。主因：工具错误分类。**

当前 interact 在缺 FrameId 时尚未执行 DOM 交互，却落入统一 catch：“结果可能部分生效，请先观察现状”。这让模型对一个确定的入参错误也要重新观察，增加往返。

应区分 INVALID_ARGUMENT/未派发、派发后业务效果待验、超时效果未知。发送后超时的谨慎提示必须保留；不能让所有失败共享同一个不确定性描述。

### 5. 打招呼、副作用与结果核验

**18｜将 is-disabled 从临时禁用误判为已发送状态。主因：模型证据推断。**

L293 将该 class 当作“已经打过招呼”的指示；L323 关闭弹窗后 class 消失，反证它至少不是稳定持久状态。模型及时注意到矛盾是好事，但这个结论若进入技能会误导去重。

需要明确状态生命周期：发送中/弹窗期间禁用、业务已发送、消息送达是不同状态。class 只能作为当次辅助线索，不能独立决定再次发送或跳过。

**19｜讨论甚至可能探索重复点击，违反最小副作用原则。主因：模型策略与去重方法不足。**

L323–343 多次考虑点击同一个岗位验证幂等性。L426–442 后有点击和脚本调用，但缺少入参，无法确认是否真的重复点击同一沟通按钮。应区分风险讨论与已发生行为。

不管本次最终是否重发，都不能依赖“网站一般会去重”来进行真实消息试验。一次点击后无新弹窗也不证明服务端没有再次发送。去重必须基于稳定岗位/会话身份和业务回执；效果不明时先核对，不重放。

**20｜自动发默认招呼语是必要知识，但消息内容约束未被完整表达。主因：任务规格与技能。**

记录发现“立即沟通”会直接发送默认文案，省去单独发送步骤，这项发现有价值。但技能应在动作之前告诉执行者这个入口有发送副作用，并说明默认文案与用户指定文案之间的处理关系。

本次用户要求打招呼，记录不足以认定发送本身越权；问题是不能让未来执行者将“打开沟通界面”误以为只读动作。

**21｜消息列表顶部及时间只能辅助识别，不能独立绑定岗位。主因：结果核验策略。**

验证用顶部“公司/HR + 送达 + 时间”核对本次操作，并花很多文字排除历史会话。实时列表可能插入其他消息，同公司同 HR 也可能关联多个岗位。

更稳妥的是行动前记录岗位稳定标识、公司和招聘者，行动后关联会话上下文或消息回执。无法完整关联时应报告“疑似对应/证据不足”，而非仅凭位于顶部就认定目标岗位已送达。

**22｜重新加载后的列表排序变化没有形成稳定恢复方法。主因：模型策略与技能缺失。**

L381 之后按原岗位名搜索得到零命中，表中却存在别的岗位。可能是尚未加载到原记录、排序变化或筛选状态变化；零命中不代表岗位不存在，也不代表已发送状态改变。

原岗位身份与来源 URL、已处理集合、恢复位置应在行动前记录。列表行号、当前位置、标题片段均不足以单独承担断点恢复。

### 6. 标签页、等待与输出成本

**23｜导航与标签切换语义会打乱“当前页”的假设。主因：工具契约及实现。**

验证 L557 产生新标签，L700 附近消息导航又激活旧标签。新页面、复用旧页和刷新当前页是不同操作，模型却需要不断重新推测当前上下文。

当前 navigation.ts 还存在可直接核对的契约问题：说明称 newTab=false 使用当前标签，但实现先搜索并激活同 URL 标签，再判断 newTab。因此指定 false 也可能切走。此缺口不依赖本次缺失的入参即可从源码确认；但不能断言本次调用一定传了 false。

应显式区分当前标签导航、创建、复用并固定优先级，返回实际行为和 tabId。会话应绑定学习来源标签与核验标签，使用返回标识恢复，而不是凭 URL 或旧活动标签猜测。

**24｜派发成功、页面加载完成和业务成功需要分层等待。主因：交互策略。**

本次点击后检查详情标题、弹窗、送达状态是正确的。另一方面，连续读取 page_info、整页文本、脚本，再临时决定看什么，增加调用成本。每个动作应先选定一个主要业务后置条件，必要时再补证据。

waitForLoad 或 click success 不等于 SPA 数据已经稳定；固定 sleep 也不是业务证明。应有短时、有限的条件等待，并在超时后报告实际观察状态。

**25｜脚本结果双重编码、完整工具封装回送增加了认知负担。主因：模型调用形态与共享结果序列化。**

L197–207 能看到脚本 result 是 JSON 字符串而不是对象，同时 content.text 和 data 又各包含一份结果。当前 conversation-engine.ts 直接 JSON.stringify 完整 ToolResult 回送模型，会保留这类重复结构。

模型应优先 return 对象而不是 JSON.stringify 对象；工具与编排应分别保留机器消费数据和紧凑的模型视图，避免无意义重复，但不能牺牲结构化回执、错误状态或追踪证据。是否所有协议都重复、实际多花多少 token，需要请求日志计量，不能从导出文本估算准确倍率。

**26｜字体映射造成的薪资乱码没有被明确归入不可读字段。主因：页面文本感知边界。**

L207、观察表的薪资含私用区字形，说明纯 DOM 文本不能直接恢复真实数字。本次目标没有薪资条件，因此不必为它额外绕路；但若今后任务按薪资筛选，不能猜测数值或把乱码写成有效数据。

技能应记录当前能力边界；需要该字段时选合法可用的数据通道或请用户提供信息，不用不确定内容做匹配判定。

### 7. 记录、收尾与验证判定

**27｜计划维护过密，证据记录偏少。主因：引导粒度与模型分配策略。**

验证 49 次调用中 16 次为 plan_tool，约三分之一；只出现一次 note_tool，集中在末尾记录问题。调用详情缺失，不能把连续 plan_tool 直接定性为重复无效调用，也不能认为一次 note 只能写一条。

但是“每发现一个问题立即留证据”的目标与实际可见过程不一致。应按阶段或重要状态变化维护计划，问题发现时保存紧凑证据；不需要为每个微步骤额外做多次计划更新。

**28｜触限后临时强制提交，产出依赖回忆，且缺少可见提交依据。主因：当时的编排。**

L446 明确到循环守卫，L455–465 要求只调用 submit_skill，随后立刻提交。强制收尾能避免没有成果，比空结束好；但不能修复此前的探索失控。

当前已有继续、总结、丢弃的用户选择，此项历史行为已调整。仍应保证总结拿到本阶段的实际证据与覆盖限制，不把“必须交稿”转成“必须成功”。本记录未展开提交正文，无法核对强制收尾是否恰好导致了 li.card-area 等错误。

**29｜验证环境能力大于技能声明能力，造成可用性假阳性。主因：验证编排与依赖一致性。**

记录明确发现正文依赖 browser_page_exec、browser_switch_tab，但 allowed-tools 未声明；验证环境仍可调用这些工具。当前 siteValidateText 同样提供完整的学习 DOM 基座，而非只提供该技能声明的执行依赖。reconcileSkillDraft 主要去重及剥离不合模式工具，不检查正文依赖是否完整。

这不应直接叫“越权漏洞”：本项目 allowed-tools 是预授权/兼容声明，并非简单等同于会话安全沙箱。问题是验证成功并不能证明技能在声明兼容的执行环境中可用。

应将严格复现与诊断分开：主流程在声明依赖及固定基础能力内复现；诊断可用更广工具，但必须标记补救。修订后再次复现，才可判修订通过。不要仅用字符串扫描正文就自动扩大预授权，示例和反例也可能出现工具名。

**30｜发现实质错误后没有修稿，原技能仍判高分通过。主因：验证标准与回执结构。**

选择器为零、调用缺必需参数、必要工具依赖未声明，都可能影响后来模型执行；它们与“搜索匹配多出一个候选”不是同一严重度。后者是动态数量，不一定需要作为错误。

模型在结束时大量讨论 issues 应为空还是改进建议、是否传评分，最后给 92 分；这反映“原稿通过”“修订后通过”“依靠人工式补救跑通”没有清楚区分。分数也没有量化依据。

当前 submit_validation 支持 revision，但它可选；issues 在 passed=true 时统一展示为改进建议，编排未结构化区分未解决阻断、一般建议和已修复问题。仍可能出现同类放行。当前修订还禁止修改 allowedTools，因此遇到必要依赖缺漏，应改写正文使用已声明能力并复验，或判不通过交回学习，不应把环境额外能力当作原技能能力。

**31｜验证只覆盖单条主路径，却宣称通用性较高。主因：验收证据不足。**

验证确实完成一次新岗位的详情切换、打招呼及消息核验，这是有价值的端到端样本。但未展示稳定业务 ID 去重、断点恢复、已沟通过状态识别、单条失败隔离等完整循环机制证据。

因此应报告“主路径样本通过，若干复用机制未证实”，而不是用滚动到 300 或逐字匹配弹窗替代通用性证明。不需要额外制造验证码、强行投递或反复给同人发消息来填齐覆盖表。

**32｜长篇反复决策让流程看起来不受控制。主因：模型输出策略，产品展示可能放大。**

L711–796 对是否再发、1 个是否足够、issues 应如何写多次反复。该讨论没有持续引入新证据。它消耗推理预算，也妨碍用户判断任务是否仍在推进。

应在阶段开始确定副作用预算与通过标准；执行中记录“已决定什么、依据是什么、什么新证据才重开决策”。面向用户只汇报发现、动作和限制。若长文本来自 reasoning，应按产品规则清楚折叠区分；若来自正文，应约束正文更新方式。缺少原始流字段前不能认定是渲染 bug。

## 不应误判为问题的行为

- 点击后检查业务结果，而非相信 click dispatched，本次做对了。
- 检查详情面板而非只看 URL，适合 SPA 场景。
- 发现自动发送、弹窗按钮实际分为两个、禁用态不持久，都产生了有价值的现场知识。
- 使用 URL 参数或短脚本不是天然违规；关键是有证据、可恢复、必要且符合执行模式。
- 验证在原选择器失效后使用其他线索诊断，具有价值；问题出在诊断成功被记成原技能无修改通过。
- 最终选择不继续无意义发送是正确方向，虽然决策出现得太晚、反复过多。
- 工具报错并可恢复本身不等于产品失败。需要治理的是可预防的契约误用、无信息增量的重复和错误的成功判定。

## 建议的修复优先级

### 优先一：先使“验证通过”可信

1. 将原稿复现、诊断补救、修订复验分开记录；未修复的必要依赖或默认路径错误不能仅包装成建议。
2. 给问题增加解决状态与影响范围，明确当前结论针对原稿还是修订稿。评分可暂时省略，避免无证据的精确数字。
3. 验证环境与技能声明依赖做一致性检查；诊断工具可保留，但不计入严格复现成功。
4. 给有副作用动作建立稳定对象身份与结果账本，效果不明时只读核验，禁止用重复点击测试平台幂等性。

### 优先二：修共享工具的可预测性

1. 对齐当前标签导航与复用语义。
2. 明确文档滚动仍需 frame 路由；区分参数拒绝、未派发、已派发及效果未知。
3. 观察区分语义角色与真实标签，零命中结果优先简洁展示。
4. 评估纯文本 hover 的真实实现和模式边界；不能只在 prompt 写一个工具不具备的动作。
5. 精简模型端工具结果，保留必要结构、回执与调试证据；避免强制 JSON 字符串套 JSON 字符串。

### 优先三：减少绕路，而非继续堆 prompt

1. 初始计划明确知识目标、代表性样本、副作用预算与停止条件。
2. 先完成一个小闭环，再补差异；只读诊断合并，依赖动作逐步执行。
3. 知识记录采用“已证实 / 假设 / 被反证 / 未覆盖”状态。反证必须更新结论，不能与旧结论并存流入技能。
4. 计划按阶段更新，事实按关键证据记录；不机械地每一步都维护多个工具状态。
5. 技能写稳定规则和条件，不写固定命中数、固定总量、特定 HR/账号、一次性 class 状态。
6. 在会话中记录 build/prompt/schema 版本及实际工具面，避免无法判断“源码已修、运行仍旧”的情况。

不建议的方向：自动忽略所有多余参数、默认补 frameId=0、无限提高超时、删除所有页面脚本能力、把技能里出现的所有工具名自动加进预授权、通过反复发送验证去重。这些做法会把局部问题变成更难察觉的状态或权限错误。

## 本任务更合理的一次学习流程

1. 确定目标为“杭州 AI 实习岗位的搜索、匹配、逐条打招呼方法”；明确只做代表性探索，真实发送预算单独控制。
2. 首页只读核对登录与城市，定位搜索框，输入任务关键词，确认结果条件。
3. 验证实习筛选：优先可执行 UI 路径；若纯文本能力不足，验证 URL 快捷路径并记录边界。
4. 读取少量不同岗位，建立稳定身份，确认标题与详情绑定；少量加载验证列表增量，不先滚满。
5. 对允许且未处理的匹配对象执行一次必要动作，核对自动发送、弹窗及对应会话回执；更新处理账本。
6. 换不同状态/样本验证定位、循环和恢复，已有写操作只读核对。未覆盖分支诚实记录，不制造异常。
7. 回验定位规则及必要工具依赖，产出参数化技能。去掉过程日志、硬编码人数、固定列表总量与未经证实的服务端保证。
8. 验证从起点重建上下文；原稿出错先留证据，有界修订后复验。结果明确是原稿通过、修订通过还是证据不足。

这里的重点不是规定死调用次数，而是**每次观察解决一个具体不确定性，每个动作验证一个业务变化；证据足够即停止，没有新证据就不反复重开同一决策。**

## 外部实践对照

Playwright 官方建议优先用户可感知的属性与明确契约来定位，并用作用域与语义消歧，避免依赖脆弱 DOM 结构；其条件等待和可重试断言也支持“等待业务状态，而非猜固定延迟”的方向。这里借鉴原则，并不要求项目迁移到 Playwright。

- [Playwright：Best Practices](https://playwright.dev/docs/best-practices)
- [Playwright：Locators](https://playwright.dev/docs/locators)
- [Playwright：Auto-waiting](https://playwright.dev/docs/actionability)

AWS 的幂等重试实践以明确操作身份和已定义的服务端契约为基础；不能据一次无弹窗或一般印象推断第三方发送操作可安全重放。这是本报告对重复打招呼风险的工程依据，不是对 BOSS 实际去重实现的断言。

- [AWS Builders’ Library：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

最终判断：本次不是单个参数错误导致的绕路，而是**探索范围、网页状态模型、依赖契约和验证证据标准未形成闭环**。先修这些闭环，再做提示词精简，才能降低调用量并提高学习成果的可复用性。
